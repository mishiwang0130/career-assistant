# 技术约定

本文档记录 M1 建立并冻结的账号与技术底座约定，后续模块直接复用，不重复定义。

## 统一响应

所有接口响应体统一使用 `Result<T>`：

```json
{
  "code": 200,
  "msg": "成功",
  "data": {}
}
```

- 成功固定为 HTTP 200 且 `code = 200`。
- 业务异常（`BizException`）**一律返回 HTTP 200**，失败语义全部由自定义 `code` 表达，前端按 `code != 200` 判断失败。业务代码不得再为 `BizException` 指定 HTTP 状态。
- 错误响应体仍然是 `Result`，`data` 为 `null`。
- 唯一例外是**鉴权拦截器**：请求未携带或携带无效令牌时，拦截器直接写出 HTTP 401（不经过 `BizException`），前端据此触发令牌刷新或跳转登录。
- 框架层映射保持 HTTP 语义：参数校验失败 400、路由资源不存在 404、未捕获的系统异常 500。
- Controller 只负责参数校验和调用 Service，不在 Controller 内拼装业务错误。

## 错误码

`ErrorCode` 只保存 `code` 和 `msg`，不携带 HTTP 状态。

```java
public final class ErrorCode {
    private final int code;
    private final String msg;
}
```

错误码实例统一放在 `ErrorConstant`，业务代码使用：

```java
throw new BizException(ErrorConstant.USERNAME_ALREADY_EXISTS);
```

`BizException` 一律返回 HTTP 200，业务错误全部通过 `ErrorCode.code` 区分，不再显式指定 HTTP 状态。HTTP 状态码只表达框架层语义：Bean Validation 参数校验失败 400、路由不存在 404、未捕获异常 500，以及鉴权拦截器在未登录或令牌失效时直接输出的 401。

下表的 HTTP 列表示该错误最终响应的状态码：由 `BizException` 抛出的一律为 200，其余为框架层映射结果。

| code | msg | HTTP | 说明 |
|---|---|---|---|
| 200 | 成功 | 200 | 成功响应 |
| 400 | 参数错误 | 400 | 参数校验或请求体解析失败 |
| 401 | 未登录或登录已过期 | 200 | 业务异常由 code 区分；拦截器拦截未通过鉴权的请求时直接写 HTTP 401 |
| 403 | 无权限 | 200 | 业务异常，由 code 区分 |
| 404 | 资源不存在 | 404 | 路由或静态资源不存在 |
| 500 | 系统异常 | 500 | 未捕获的系统异常 |
| 1001 | 用户名已存在 | 200 | 业务异常，由 code 区分 |
| 1002 | 用户名或密码错误 | 200 | 业务异常，由 code 区分 |
| 1003 | 账号已禁用 | 200 | 业务异常，由 code 区分 |
| 1004 | 刷新令牌无效或已过期 | 200 | 业务异常，由 code 区分 |
| 1050 | 会话正在处理中，请稍后再试 | 200 | 同一会话已有请求在处理，业务异常由 code 区分 |

后续模块只追加错误码，不复用已有编号，不修改已有编号含义。

## 鉴权约定

- 请求头：`Authorization: Bearer <accessToken>`。
- Access Token 是 JWT，payload 至少包含 `userId`、`username`、`jti`、`iat`、`exp`。
- JWT 密钥来自 `JWT_SECRET`，有效期来自 `JWT_ACCESS_EXPIRE_MINUTES`。
- 服务端使用 `sys_token.jti` 校验 Access Token 是否有效、未撤销、未过期。
- Refresh Token 只保存 SHA-256 摘要，原始值只返回给客户端。
- 刷新使用轮换策略：撤销旧 Access Token 和旧 Refresh Token，签发新 token 对。
- 退出登录撤销当前 Access Token 及其关联 Refresh Token。
- 允许多端登录，每次登录创建独立的 token 对。

配置项：

```yaml
app:
  jwt:
    access-token-expire-minutes: ${JWT_ACCESS_EXPIRE_MINUTES:120}
    refresh-token-expire-days: ${JWT_REFRESH_EXPIRE_DAYS:7}
```

## Redis key 规范

所有 Redis key 必须统一为：

```text

```

公共前缀常量：

```java

```

本模块未使用业务 Redis key，`RedisUtil` 供后续模块复用。

Redis 客户端统一使用 `StringRedisTemplate`，Redis 中保存的是 JSON 字符串，不再配置 `RedisTemplate<String,Object>` 的默认类型序列化。`RedisUtil` 通过 Spring 容器中的 `ObjectMapper` 统一完成对象与 JSON 的互转。

RedisUtil 按 Redis 数据类型提供独立方法：

| 类型 | 方法 |
|---|---|
| String | `set`、`setIfAbsent`、`get`、`delete`、`expire`、`hasKey` |
| Hash | `setHash`、`getHash`、`getHashAll`、`hasHashKey`、`deleteHash` |
| List | `setList`、`getList`、`pushList`、`sizeList` |
| Set | `addSet`、`getSet`、`hasSetMember`、`removeSet`、`sizeSet` |
| ZSet | `addZSet`、`getZSetRange`、`getZSetScore`、`removeZSet`、`sizeZSet` |

带过期时间的 String 写入方法固定为：

```java

```

其中 `timeout` 为 `long` 数值，`timeUnit` 为 `java.util.concurrent.TimeUnit`。

# M2 冻结的约定

本文档以下内容由 M2「Agent 内核与对话通道」建立并冻结，后续模块直接复用，不重复定义。

## SSE 事件协议

事件名与顺序固定，前端按事件名分流：

| 事件 | data 结构 | 说明 |
|---|---|---|
| `meta` | `{scene, sessionId, provider, messageId}` | 流开始，必为第一个事件 |
| `delta` | `{content}` | 文本增量 |
| `thinking` | `{content}` | 思考增量，模型不支持时不发 |
| `tool` | `{name, status, detail}` | 工具调用开始 / 结束，status 为 `START` / `END` |
| `node` | `{name}` | 触发子智能体 |
| `result` | `{data}` | 最终结构化结果，纯文本场景不发 |
| `done` | `{}` | 正常结束，必为最后一个事件 |
| `error` | `{message}` | 异常结束，与 `done` 互斥 |

边界规则：

- SSE 接口不返回 `Result` 包装：进流前仍按统一响应约定返回 `Result`（未登录 401、参数校验失败 400、业务异常 HTTP 200 + 非 200 的 `code`）；一旦流开始，只能用 `error` 事件表达失败，不再改 HTTP 状态码。
- 前端要同时处理"进流前拿到 `Result` 错误"和"进流后拿到 `error` 事件"两种情况。
- 心跳使用 SSE 注释行（`:heartbeat`），不占用事件名，前端解析时忽略注释行。
- `error` 事件覆盖三类来源：流内异常、`ExceedMaxItersEvent`（超过 `max-iters`）、流超时。
- 事件载荷为单行 JSON，`event:` / `data:` 行的拼装由 Spring `SseEmitter` 完成，后端不手工拼接报文。

**为什么需要 `AgentEventMapper`（适配层说明）**：框架提供的流式能力是**事件流**——`HarnessAgent.streamEvents(Msg, RuntimeContext)` 返回 `Flux<AgentEvent>`，本项目直接使用，Agent 的推理、工具调用、步数控制全部由框架驱动，没有自建任何流式机制。但框架**不提供面向浏览器的 SSE 服务端协议**：核对 2.0.3 的 core / harness 后，与 SSE 相关的只有两处，都不是本场景可复用的能力——

- `io.agentscope.core.tool.mcp.McpClientBuilder$SseTransportConfig`：MCP **客户端**侧传输（连别人的 MCP 服务端）；
- `io.agentscope.harness.agent.subagent.task.AgentProtocolTaskClient#openEventStream`：远程子智能体任务的 SSE **客户端**（消费 `RemoteAgentEvent`，字段含 taskId / seq / agentId，事件类型为 `RUN_STARTED` / `TEXT_DELTA` / `TOOL_CALL_START` …）。

本项目的 `delta / thinking / tool / node / result / done / error`、data 结构、与 `Result` 的边界规则是对外冻结契约（前端直接依赖），属于产品协议而不是框架内部协议，因此需要一层薄适配：`AgentEventMapper` 只做 `AgentEventType → 协议事件`的类型映射（无状态、无业务逻辑，其余事件类型直接忽略），SSE 报文仍由 Spring `SseEmitter` 生成。若后续框架提供官方 SSE 协议接入，再评估替换。

## Tool 命名与注册规范

- 所有 Tool 实现统一放在 `com.wxy.career.tool` 包，禁止放在 `util`、`service` 或其他包。
- 命名用 snake_case，动词开头：`get_current_user`、`search_question_bank`。
- 工具方法用 `@Tool(name, description, readOnly)` 标注，参数用 `@ToolParam(name, required, description)` 描述；框架不支持的上下文对象（`RuntimeContext`、`ToolExecutionContext` 等）直接作为方法参数注入。
- 每个 Tool 明确标注是否只读：只读工具在 `EXPLORE` / `ACCEPT_EDITS` 权限模式下自动放行，写工具受策略管控。
- 入参出参使用简单类型或独立 DTO，禁止直接返回 `po` 实体。
- 每个 Agent 通过 `Toolkit.registerTool` / `registerAgentTool` 注册**自己的**工具白名单，不允许所有 Agent 共享全部 Tool。
- M2 只注册只读工具 `get_current_user`（读取当前登录用户 ID 与昵称，用户身份取自 `RuntimeContext`，不接受模型传入的 userId）。

## Agent 命名与 RuntimeContext 约定

- 主 Agent 名固定为 `career-assistant`，场景名为 `assistant`。
- 每次调用必须携带 `RuntimeContext(userId, sessionId)`，二者都不能为空，缺失时抛业务异常。
- `userId` 一律从 `LoginUserHolder` 获取，**绝不接受前端传入的 userId**；SSE 异步执行前先在请求线程取好用户身份。
- 会话状态存储的键就是 `(userId, sessionId)`，用户隔离由 AgentScope 自身保证，不需要额外的命名空间拼接。
- 新增 Agent 时先在本文档登记 Agent 名与场景的对应关系，再写代码。

## 会话与存储约定

- Agent 会话状态固定存放在 Redis：`RedisAgentStateStore`（Redisson 客户端）+ `AgentScopeExpiringStateStore` 续期 TTL。
- **为什么需要 `AgentScopeExpiringStateStore`**：框架的 `RedisAgentStateStore` 只负责存取——它的 Builder 只有 `keyPrefix` 与客户端选项（`jedisClient` / `lettuceClient` / `redissonClient` / `clientAdapter`），`RedisClientAdapter` 也没有 `expire` 方法，2.0.3 全部 jar 中带 TTL 概念的只有 sandbox 快照（`RedisSnapshotSpec`）。若不额外加这一层，`career:agent:{userId}/{sessionId}:*` 会永不清理。本类只在写路径（`save` / `saveIfVersion` / 单键 `delete`）续期 TTL，读路径（`get` / `getVersioned` / `getList` / `exists` / `listSessionIds` / `close`）全部直接委托框架实现；若框架后续为 Redis 状态存储提供 TTL 参数，删除本类改为直接用框架配置。
- Redis key 前缀为 `career:agent:`（`RedisKeyConstants.AGENT`），槽位格式为 `{前缀}{userId}/{sessionId}`，同槽位的键形如 `:list`、`:{状态名}`，另有 `{前缀}{userId}:_keys` 记录该用户的会话 ID 集合。
- 每次写会话状态后按槽位刷新 TTL（配置项 `app.agent.session-ttl-hours`），刷新失败只打日志，不阻断对话。
- 会话消息另存 MySQL 表 `assistant_message`，用于历史分页；清空会话时同时逻辑删除该表消息并清理 Redis 中的会话状态。
- 后续模块的 memory、skill 数据同样落 MySQL 表，本模块只登记约定，不建表。
- SSE 心跳与超时调度使用独立线程池（`sseTaskScheduler`），不使用 `Executors` 创建。

## 框架原生能力使用约定

**总原则：AgentScope 2.0.3 已有原生能力的一律用框架实现，禁止自建重复轮子；框架确实不具备的能力才自己写，并在本文档登记理由。**

已核实可用的能力（用 `javap` 核对 2.0.3 jar 得出）：

| 能力 | 框架类型 |
|---|---|
| Agent 主入口 | `HarnessAgent` 与 `HarnessAgent.Builder`（内部委托 `ReActAgent`） |
| 流式事件 | `streamEvents(...)` 返回 `Flux<AgentEvent>`（本项目直接使用）、旧 API `stream(...)` 返回 `Flux<Event>`、`ChatUiChannel.sendStream(...)`；三者都只是**事件流**，框架不提供 SSE 服务端传输 |
| Skill | `AgentSkill`、`AgentSkillRepository`、`ClasspathSkillRepository`、`FileSystemSkillRepository`、`MarkdownSkillParser`、`DynamicSkillMiddleware`、`SkillLoadTool` |
| Memory | `Memory`、`StateBackedMemory`、`LongTermMemory`、`MemoryConfig`、`MemoryFlushManager`、`MemorySearchTool` / `MemorySaveTool` / `MemoryGetTool` |
| Plan Mode | `HarnessAgent.enterPlanMode / exitPlanMode / isPlanModeActive`、`PlanModeManager`、`Builder.planModeEnabled` |
| 上下文治理 | `CompactionConfig`、`ConversationCompactor`、`ToolResultEvictionConfig` |
| 子智能体 | `Builder.subagentDeclarations`、`DefaultAgentManager` |
| 任务列表 | `Builder.taskRepository`、`TaskRepository` |
| 权限 | `PermissionMode`、`setPermissionMode` |
| MCP | `McpClientBuilder`（Stdio / SSE / StreamableHttp 三种传输）、`McpClientManager`、`McpTool`、`McpServerRegistrar` |

落位要求：

- Skill 走框架的 `AgentSkillRepository` 抽象，技能内容为 Markdown，默认用 `ClasspathSkillRepository` 放在 `resources/skills/`；需要运营化时实现该接口的 MySQL 版本，仍走框架接口，不自造 Skill 体系。
- 长期记忆优先使用框架 `LongTermMemory`；采用外部记忆服务时按下一节的方式通过 MCP 接入。
- Plan Mode、Compaction、Tool Result Eviction、Task List、子智能体一律使用 `HarnessAgent` 的对应配置项，不自己写状态机。

**现状与迁移**：M2 的 `career-assistant` 已由 `HarnessAgent` 构建（`AgentFactoryImpl.buildAgent`），对外行为与迁移前一致：同样的 SSE 事件序列、同样的工具白名单、同样的 Redis 会话状态。第一版只站上框架扩展点，用不到的默认能力显式关闭：

| 关闭项 | Builder 开关 | 理由 |
|---|---|---|
| 文件读写工具 | `disableFilesystemTools()` | 向模型暴露本机文件系统是纯风险，本模块不需要文件能力 |
| Shell 工具 | `disableShellTool()` | 禁止在应用进程内执行命令 |
| 工作区上下文 | `disableWorkspaceContext()` | 提示词在 YAML、技能走仓库、记忆交 ReMe，不需要注入工作区文件内容 |
| @ 路径展开 | `disableAtPathExpansion()` | 依赖工作区文件读取，关闭后不会展开消息中的 @ 路径 |
| 动态技能与默认工作区技能 | `disableDynamicSkills()`、`disableDefaultWorkspaceSkills()` | Skill 由 M14 认领后再打开 |
| 子智能体 | `disableSubagents()` | 由 M8 认领后再打开 |
| 会话转录文件 | `disableTranscript()` | 会话消息已落 MySQL，转录文件会往工作区写文件 |
| 记忆工具与记忆钩子 | `disableMemoryTools()`、`disableMemoryHooks()` | 长期记忆由 M11 接 ReMe，框架自带的文件式记忆暂不启用 |

保留框架默认：`CompactionConfig` 与 `ToolResultEvictionConfig`（实测短对话下不改变 SSE 事件序列、不产生落盘，后续由 M13 调优）、Agent 逐步 trace 日志（`AgentTraceMiddleware`，INFO 级，用于排查推理步骤）。

**工具白名单（冻结约定）**：`HarnessAgent` 默认可注册 Web 工具与平台工具，仅靠关闭开关不足以收窄，因此每个 Agent 都必须通过 `Builder.toolsConfig(ToolsConfig)` 声明白名单：

- `allow` 取当前 `Toolkit` 的工具名集合，工具列表只有一个来源，不在两处维护；
- 框架「平台工具」不受 `allow` 约束（`ToolFilter` 只按 `deny` 移除平台工具），不需要的平台工具必须显式 `deny`，当前为 `wait_async_results`；
- 新增平台工具时同步维护 deny 列表；`AgentFactoryHarnessTest` 断言最终工具集只包含白名单工具，防止框架默认工具混入。

## workspace 说明

- 本项目**不往 workspace 放任何业务内容**：技能走 `AgentSkillRepository`，系统提示词在 `application.yml`，长期记忆交给 ReMe，会话消息在 MySQL，会话状态在 Redis。
- 不新增 `app.agent.workspace` 之类的配置项，也不显式指定路径：`HarnessAgent` 未配置时按 `agentscope.workspace` 系统属性 → `AGENTSCOPE_WORKSPACE` 环境变量 → `{user.dir}/.agentscope/workspace` 依次解析默认根目录，`{user.dir}` 下的 `.agentscope/` 已被 `.gitignore` 忽略。
- 实测结论（AgentScope 2.0.3，2026-09-28）：在上面那批 `disable*` 开关生效且工具白名单收窄后，构建 Agent 与完成一轮对话都不会在 workspace 创建任何文件（包括 `AGENTS.md`、`MEMORY.md`、`memory/`、`sessions/`、`skills/`）。因此保持「不配置 workspace」方案，不引入内存文件系统：`filesystem(new RemoteFilesystemSpec(new InMemoryStore()))` 要求状态存储是非本地的分布式实现（测试用的 `InMemoryAgentStateStore` 会让构建直接失败），且其 `WorkspaceIndex` 仍会在工作区落一个本地 `.index/workspace.db`。
- 能力认领关系：Plan Mode → M10，Memory → M11，Compaction / Tool Result Eviction → M13，Skill → M14，SubAgent → M8；打开对应能力时同步补测试并更新本节。

## 长期记忆（ReMe）

选型：长期记忆使用外部记忆服务 **ReMe**，不自建记忆表结构。

- ReMe 是 Python 3.11+ 服务（PyPI `reme-ai`），以 Markdown 文件为记忆载体，检索为 BM25 加可选向量与 wikilink 扩展，必须作为**独立进程**部署。
- Java 侧对接方式：优先 **MCP**（用 `McpClientBuilder` 连接 ReMe 的 MCP 服务，把记忆检索与写入工具注册进 Agent 的白名单）；HTTP 作为兜底方案。
- 与框架的分工：长期记忆交给 ReMe，替换框架自带的文件式长期记忆；Skill、Plan Mode、Compaction 仍用框架能力。
- Qdrant 不承担长期记忆（ReMe 自带检索与索引），只用于题库与知识点检索。

实现前必须逐条确认的约束：

1. **用户隔离**：记忆必须按 `userId` 隔离，禁止跨用户召回；ReMe 的隔离机制需在接入前验证并补记到本文档。
2. **降级**：ReMe 不可用时对话主流程不中断，检索失败降级为"无长期记忆"，写入失败只记日志。
3. **写入门槛**：模型自动写入的记忆只限稳定偏好与长期薄弱点，不写入原始问答全文。
4. **可观测**：记忆读写进入日志与埋点，便于演示"记忆影响了下一轮回答"。

## 并发与限流约定

- 会话 ID 只允许 `[A-Za-z0-9_-]{1,64}`：它参与 Redis key 拼接与 SCAN 模式匹配，必须防通配符注入。
- 同一会话串行处理：以 `career:agent:lock:{userId}/{sessionId}` 为键 `setIfAbsent` 抢占，抢不到直接返回 1050 而不排队；租约取流超时时间加 60 秒，持有者令牌匹配才允许释放。
- 会话状态的 TTL 续期按槽位节流（60 秒窗口），避免每次状态写入都做一次键空间扫描；扫描结果为空时打 warn，用于及早发现 AgentScope 内部键格式变化。

# M4 冻结的约定

本文档以下内容由 M4「简历管理与解析」建立并冻结，后续模块直接复用，不重复定义。

## 文件存储约定

- 原始文件统一存放 MinIO，业务表只保存 `object_key` 与文件元数据，不保存物理地址或预签名地址。
- 对象 key 固定为 `{bizType}/{userId}/{yyyyMM}/{uuid}.{ext}`，`bizType` 只允许 `[A-Za-z0-9_-]+`，简历模块使用 `resume`。
- 物理对象名一律 UUID 化，原始文件名只经过安全化后保存为 `file_name`，仅用于展示。
- 扩展名白名单固定为 `pdf`、`doc`、`docx`、`txt`、`md`；单文件上限 10MB。
- 文件校验同时使用扩展名白名单与文件头魔数：PDF 校验 `%PDF-`，DOC 校验 OLE2 头，DOCX 校验 ZIP 头，TXT/MD 校验严格 UTF-8 且不含 NUL；不信任前端 `Content-Type`。
- 对外访问文件统一走后端接口，并按 `id + user_id` 做鉴权与越权校验；本模块未开放下载接口，但后续实现下载时必须遵守该约定。
- `FileStorage` 位于 `common/storage`，业务模块只依赖接口；MinIO 实现为 `MinioFileStorage`。

## 简历状态与来源

| 类型 | 取值 | 说明 |
|---|---|---|
| `source_type` | `UPLOAD` / `MANUAL` | 文件上传 / 在线填写 |
| `parse_status` | `PENDING` / `SUCCESS` / `FAILED` | 待解析 / 解析成功 / 解析失败 |

- 上传与在线填写均同步返回结果；解析失败不抛异常给前端，而是返回成功响应并携带 `FAILED` 状态与 `parse_error`。
- 在线填写和编辑非空正文后，解析状态统一为 `SUCCESS` 并清空 `parse_error`。
- `is_default` 只通过显式“设为默认”接口变更，不自动设置或迁移。

`MINIO_ACCESS_KEY`、`MINIO_SECRET_KEY` 在所有 Profile 中都只从环境变量读取，任何 YAML 中都不允许写真实密钥。

## 接口清单（M4 新增）

| 接口 | 方法 | 认证 | 说明 |
|---|---|---|---|
| `/api/resumes/upload` | POST multipart | 是 | 上传并同步解析，解析失败仍返回成功与 `FAILED` 状态 |
| `/api/resumes/manual` | POST | 是 | 在线填写或粘贴文本 |
| `/api/resumes` | GET | 是 | 列表，不返回 `rawText`，默认优先、创建时间倒序 |
| `/api/resumes/{id}` | GET | 是 | 详情，包含 `rawText` |
| `/api/resumes/{id}` | PUT | 是 | 更新标题或正文 |
| `/api/resumes/{id}` | DELETE | 是 | 逻辑删除 |
| `/api/resumes/{id}/default` | PUT | 是 | 设为默认 |

所有查询、更新、删除和默认设置都必须同时使用 `id` 与当前登录用户的 `user_id`；跨账号访问统一返回 1201，不暴露资源是否存在。
