## 三、实现思路

### 3.1 两个 Agent 都不是会话

- 计划 Agent `planner` 由计划页按钮触发，运行标识固定 `sessionId = training-plan-{userId}`（非会话也需要一个稳定的状态槽位）；
  提示词 `prompts/planner.md`，技能 `training-planning`（MySQL 技能仓库，热更新）。
- 提醒 Agent `reminder` 由 Quartz 每天 08:00 触发一次，由调度扩展按 `AgentConfig` 现场构建（提示词 `prompts/reminder.md`，
  模型复用 `AgentScopeConfiguration` 装配的实例），工具只有 `list_planned_users` 与 `save_training_reminder`。

### 3.2 计划正文只进 MySQL，而且只存一份正文

- **没有任务表**：一份计划就是一条 `training_plan`，`plan_content` 是「一天一行、一句话概括」的短正文。
  起止日期与每天时长来自用户在计划页填写的表单，由服务端落库，模型不参与。
- 模型通过写工具 `submit_training_plan(planContent, adjustmentReason?)` 只提交这一段文本；
  服务端在一个事务里「旧计划置 ENDED → 写新计划」，`adjustment_reason` 原样落库，页面在概览处展示。
- **提醒 Agent 每天读正文推断今天干什么**：简报带 `dayIndex`，Agent 取正文里对应的那一行生成提醒。
- Plan Mode 只借「只读规划阶段 + 人工确认」语义：`plan_write` 被 deny，`disableFilesystemTools` /
  `disableWorkspaceContext` / `disableAtPathExpansion` 保持不变，也没有配置 `planFileDirectory`。
- 框架默认的子 Agent 任务仓储会把任务写成工作区文件，计划 Agent 换成 `InMemoryTaskRepository`（进程内、不落盘）。

### 3.3 HITL 链路形态（两阶段 SSE，先生成草稿再确认）

1. `POST /api/plans/generation`（SSE）：跑计划 Agent。模型调用 `submit_training_plan` 时，权限上下文（`ASK`）让框架
   停下来并抛出确认请求；服务端把**计划草稿（`draftContent`）**、当前计划摘要（`existingPlan`）与提示文案
   一起下发 `result{type:"plan_confirm_required"}` + `done`，并把待确认快照写入 Redis
   `career:plan:confirm:{userId}`（30 分钟）。**此时一个字都没落库。**
   首次生成与重新规划都走这条路径——没有「首次生成自动确认」分支。
2. `POST /api/plans/generation/confirm`（SSE）：快照过期返回 1704；`approved=true` 时把
   `ConfirmResult(true, toolCall)`（消息角色 USER、metadata `agentscope_confirm_results`）回填给框架，
   同一次运行继续执行写工具，随后下发 `result{type:"training_plan"}`；
   `approved=false` 时不恢复 Agent，清掉规划态与快照，下发 `result{type:"plan_confirm_rejected"}`，**当前计划一行不改**。
3. 「未确认不保存、不覆盖」有两层保证：写工具必须过权限确认才执行；未确认路径根本不调用写工具。

### 3.4 Quartz 共库与建表

- `TrainingQuartzConfiguration` 用 `StdSchedulerFactory` 手工装配：`JobStoreTX` + `tablePrefix=QRTZ_` +
  `isClustered=false`（单实例），数据源参数取自 Spring `DataSourceProperties`（与业务同库同账号）。
- `sql/career_assistant.sql` 的 F7 段一次建全 11 张 `QRTZ_*` 表（源自 Quartz 2.5.2 的 `tables_mysql_innodb.sql`，
  去掉 `DROP`、改成 `CREATE TABLE IF NOT EXISTS`、索引内联），**会话归档总结复用**，不需要再改这段。
- 提醒幂等由 `(user_id, reminder_date)` 唯一键 + `ON DUPLICATE KEY UPDATE` 承载；
  重启时 `TrainingReminderScheduler` 先清理本扩展遗留的 Quartz 任务再重新注册，避免 JDBC 存储里的旧任务与进程内登记表不一致。

### 3.5 薄弱点只来自 MySQL

- 复用 F9 的 `get_weak_points`（读 `knowledge_mastery`），没有新增读薄弱点的工具，也没有改它的入参语义；
- 生成链路不依赖 `UserMemoryService` / `UserLongTermMemoryAdapter`（有反射断言），F7 不写记忆库。

## 四、契约变更

- 表：`training_plan`（正文在 `plan_content`）、`training_reminder` + `QRTZ_*`（框架托管表）；**没有 `training_task`**。
- 接口：`/api/plans/current`、`/api/plans/generation`(SSE)、`/api/plans/generation/confirm`(SSE)、
  `/api/plans/reminders/unread-count`、`/api/plans/reminders/{id}/read`、`/api/plans/reminders/read-all`；
  原 `POST /api/plans/tasks/{taskId}/finish`（勾选任务）随任务表一起下线。
- SSE：不改事件名与顺序，只新增 `result` 取值 `plan_confirm_required`（带 `draftContent` 与 `existingPlan`）/
  `training_plan` / `plan_confirm_rejected`。
- 错误码：1701–1704（跨账号 1051、未填求职目标 1101、参数校验 400 复用既有口径；1701 / 1702 保留占用、不再返回）。
- 配置：`app.training.plan.{max-days,min-daily-minutes,max-daily-minutes}`、`app.training.reminder.*`、
  `app.training.quartz.*`（`max-tasks` 随分配器下线一并移除）。
- Skill：新增 `training-planning`（幂等写入，`source = 'f7-training-planning'`）。

## 六、需要真实环境的验收步骤（本窗口未执行）

本窗口环境没有可用的 MySQL / Redis / `DASHSCOPE_API_KEY`，以下步骤需在具备依赖的环境执行：

```powershell
mysql -uroot -p career_assistant < sql/career_assistant.sql   # 执行两次，第二次不报错、不产生重复数据
$env:SPRING_PROFILES_ACTIVE = "local"
.\mvnw.cmd -pl backend -am spring-boot:run                    # 启动后端
curl http://localhost:8084/actuator/health                    # {"status":"UP"}
```

1. 填好求职目标、完成过一场面试（`knowledge_mastery` 里有薄弱点）→ 计划页输入「还有 7 天、每天 1 小时」→ 生成：
   弹窗里能看到思考 / 正文流式输出，结束后弹出**确认草稿弹窗**，正文按天一行、主题能对上薄弱点；
2. **确认之前先看库**：`SELECT COUNT(*) FROM training_plan WHERE user_id=? AND status='ACTIVE'` 不变（首次生成是 0），
   点「确认保存」后才有新记录；点「放弃」则一行都不写；
3. 已有计划时再点生成 → 同样先出草稿确认；确认后旧计划变成 `ENDED`、新计划带调整原因，未确认时原计划不变；
   概览里的剩余天数按截止日期实时变化；
4. 手动触发提醒（临时把 `TRAINING_REMINDER_CRON` 改到近处，或调用 `TrainingReminderScheduler.runOnce()`）→
   计划页与侧栏出现未读角标，提醒内容取自当天那一行正文，再次触发不重复
   （`SELECT COUNT(*) FROM training_reminder WHERE user_id=? AND reminder_date=?` 恒为 1）；
5. 另一个账号看不到前一个账号的计划与提醒；
6. 全流程后检查工作区：`.agentscope/` 下没有 `planner` / `training-plan` 目录与文件，数据库里能看到计划正文
   （`SELECT plan_content FROM training_plan WHERE user_id=?`）
   （本窗口已在测试链路复核这一条，见 `docs/技术约定.md` 的 workspace 复核结论）。

两条需要单独说明的验收点：

- **计划正文没有落到工作区**：`plan_write` 被 deny、计划 Agent 的任务仓储为进程内实现，计划内容只写 MySQL；
- **薄弱点只来自 MySQL**：计划 Agent 工具白名单是 `get_weak_points`（读 `knowledge_mastery`），生成链路没有任何记忆库调用。
