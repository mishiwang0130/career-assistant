## 二、实现思路

1. **Java 编排、模型只提炼**：扫描、解析、写库、重试都由服务端做，模型只把一场对话整理成 JSON。归档总结
   Agent 没有任何工具、不挂长期记忆、不启用技能与工作区，因此「模型没有写记忆的权限」在归档链路上同样成立。
2. **只归档助手会话**：讲解进度与卡点产生在 `ASSISTANT` 场景；面试会话的结论已经有 `interview_qa`、
   `knowledge_mastery`、`interview_report` 三张结构化表，再写一份记忆属于重复存储。
3. **复用 F7 的 Quartz 装配**：不新增依赖、不新建调度机制，任务与触发器仍落 `QRTZ_*` 共业务库。业务自建的
   Job 需要 Spring 注入，因此调度器挂了一个「Spring Bean 走容器、其余走 Quartz 默认工厂」的 JobFactory，
   调度扩展托管的 Agent 任务行为不变。
4. **状态机简单可查**：`PENDING` → 成功（含提炼出 0 条）置 `DONE`；失败累加 `archive_attempts`，未达上限保持
   `PENDING` 下轮重试，达到上限置 `FAILED` 并打 error 日志，避免坏会话无限消耗模型调用。
5. **「写入失败留待补偿」是真的**：`rememberFact` 返回是否真正写进 Mem0，写失败时不标记已归档，下一轮扫描
   会重试；重试时已写成功的记忆由 Mem0 自身的内容合并语义去重，不建补偿队列。
6. **格式契约按失败处理**：输出必须能解析出 `memories` 数组（允许 Markdown 代码块包裹）；解析失败不静默当成
   0 条，否则一次格式抖动就会把这场会话永久标记成已归档、记忆永久丢失。
7. **长会话只留最近内容**：对话记录超过 `max-transcript-chars` 时保留最近的轮次——归档判断「讲到哪里」靠的
   是最新几轮，同时避免超出模型上下文。

## 四、配置项

| 配置 | 默认值 | 说明 |
|---|---|---|
| `app.memory.archive.enabled` | `true` | `false` 时不注册定时任务，记忆只读不写 |
| `app.memory.archive.cron` | `0 0/30 * * * ?` | 扫描周期；可用 `MEMORY_ARCHIVE_CRON` 覆盖 |
| `app.memory.archive.zone-id` | `Asia/Shanghai` | CRON 时区 |
| `app.memory.archive.quiet-minutes` | `30` | 最后一条消息距今超过该值才算安静 |
| `app.memory.archive.batch-size` | `20` | 单次最多处理会话数 |
| `app.memory.archive.max-attempts` | `5` | 单场会话最大重试次数 |
| `app.memory.archive.max-memories` | `3` | 单场最多写入的记忆条数 |
| `app.memory.archive.max-transcript-chars` | `12000` | 送给归档 Agent 的对话记录长度上限 |
| `app.memory.archive.timeout-seconds` | `120` | 单场归档等待上限 |

`app.memory.enabled=false` 时即使归档任务已注册也会整段跳过扫描。

## 六、手工验证步骤（需要真实 MySQL / Redis / Mem0 / 模型密钥）

1. 执行 `mysql -uroot -p career_assistant < sql/career_assistant.sql`，确认 `chat_session` 出现 `archive_status`、
   `archive_time`、`archive_attempts`；重复执行脚本不报错（追加段自带 `information_schema` 判断）。数据库里已经
   执行过旧脚本时只需补跑末尾新增的这一段，历史语句不受影响。
2. 在助手会话里讲一个知识点（例如 Redis 分布式锁），留下至少一轮问答。
3. 把 `MEMORY_ARCHIVE_CRON` 调到近处、`quiet-minutes` 调小后重启（或直接调 `SessionArchiveScheduler.runOnce()`），
   日志出现「会话归档成功」，`chat_session` 里该会话 `archive_status = 'DONE'`、`archive_attempts = 1`、
   `archive_time` 非空。
4. Mem0 里能看到该用户、该会话（`runName = chat_session.id`）的 `FACT` 记忆；`PROFILE` / `WEAKNESS` 不应出现。
5. 新建一个助手会话问同一个知识点：回答应从上次中断处接着讲，不把已讲过的内容从头重复。
6. 降级：把 `MEM0_BASE_URL` 指向不可达地址后重启，归档失败但对话主流程不中断，会话保持 `PENDING` 并在下一轮
   重试，达到 `max-attempts` 后置 `FAILED`；把 `MEMORY_ARCHIVE_ENABLED=false` 则任务不注册。
7. 面试会话不被归档：走一场模拟面试并等安静阈值过去，`chat_session` 里该面试会话的 `archive_status` 仍为
   `PENDING`（本模块只扫助手场景）。

## 七、已知取舍与风险

- **只归档助手会话**：如果后续希望面试会话也沉淀记忆，改扫描场景即可，但会与结构化表重复，需要先改文档。
- **达到重试上限的会话不再自动重试**：置 `FAILED` 后需要人工排查原因，再把 `archive_status` 重置为 `PENDING`
  重跑；本批不提供管理后台。
- **重试可能重复写入已成功的记忆**：依赖 Mem0 自身的内容合并语义去重，不额外建去重表。
- **`chat_session` 归档列与 `status` 分离**：`status` 仍是会话状态，归档不改变会话可见性。
- **同一会话归档后继续追问的内容不会再次归档**：归档只处理 `PENDING` 会话，`DONE` 之后该会话新增的消息只更新
  `last_message_at`，不会再进入归档；F9 的连续讲解按文档口径走新会话、靠召回衔接。后续若要支持「同会话继续
  讲解也沉淀」，需要先把 `DONE` 且 `last_message_at > archive_time` 的会话重置为 `PENDING`，属于一次明确的
  口径变更，先改文档再改代码。
