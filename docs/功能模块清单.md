# 求职面试训练助手 · 功能模块与架构（定稿）

> 本文档是需求与架构的唯一依据，不留待定项。
>
> 划分维度是「用户能用的功能」；Harness 能力是这些功能的实现手段，集中在第 6 节，不单独作为模块排期。
>
> 第 8 节是优先级与依赖，第 9 节是总排期，第 10 节是协作约定（哪些必须上收、哪些下放给开发窗口）。

## 1. 项目定位

网页版求职面试训练助手，多人在线使用、数据按账号隔离，部署在服务器上，不是安装在用户本地的工具。本项目同时是 AgentScope Java 2 Harness 的实践项目：**框架能力尽量用，但每一项都必须有真实业务场景支撑。**

用户使用链路：

1. 上传或在线填写简历（F1）
2. 填写求职目标：目标岗位、当前工作年限（F4）
3. 在助手里问：「我简历可能被追问什么」「这个 JD 我匹不匹配」「Redis 那块再讲讲」（F2 / F3 / F9）
4. 按目标岗位模拟面试，系统根据回答动态追问（F5）
5. 每轮回答得到点评，沉淀薄弱点与掌握度（F6）
6. 按薄弱点生成训练计划，随表现自动调整，每天收到当日训练提醒（F7）
7. 换会话继续练时，系统记得住薄弱点和偏好（长期记忆）

### F2 简历优化

| 项 | 说明 |
|---|---|
| 用户操作 | 在助手会话里说「诊断我的简历」，或在简历列表点某份简历的「诊断」 |
| 系统产出 | 综合得分、多维度评分（≥4 项）、问题清单、亮点、优化建议、优化后的简历正文、可能被追问的项目点 |
| 依赖 | F1 |
| 规模 | M |
| 形态 | 助手会话内，助手派发「简历分析」子 Agent 完成，结论回到对话里继续聊 |
| Harness 能力 | 子 Agent「简历分析」、Tool 读简历（分段返回，避免长简历撑爆上下文）、Skill「简历分析规范」 |

优化后的正文只作为回答内容给出，**不自动覆盖原简历**；回答下方提供「另存为新简历」按钮，点后按 F1 的在线填写方式创建一条 `source_type = MANUAL` 的简历，由用户自己决定是否设为默认。

完成情况（2026-09-29）：助手可派发「简历分析」子 Agent（`resume-analyst`，工具白名单 `read_resume` + `submit_resume_diagnosis` + 技能加载工具，技能 `resume-analysis` 存 MySQL），诊断结论随 SSE `result` 事件下发；「我的简历」列表每行有「诊断」按钮，会话仍是 `ASSISTANT`。诊断结论不落库：刷新或回看历史只剩助手正文（七块内容写全，内容不丢），卡片与「另存为新简历」按钮只在当次流中可用。错误码 1301、1302。详见 `docs/技术约定.md` 的「简历优化（F2）」章节。

### F4 求职目标（已完成）

| 项 | 说明 |
|---|---|
| 用户操作 | 在设置页填写目标岗位、当前工作年限 |
| 系统产出 | 一份供其它模块读取的求职档案 |
| 依赖 | 无 |
| 规模 | S |
| 页面 | `/profile` |
| Harness 能力 | SystemPromptMiddleware 按 RuntimeContext 注入昵称与求职目标（不注册业务工具） |
| 存储 | MySQL `user_profile`，一人一份 |
| 接口 | `GET /api/user-profile`、`PUT /api/user-profile` |
| 错误码 | 1101 求职目标未填写，供 F5、F7 校验时复用 |
| 完成情况 | 已合入 `dev`；`UserProfileService.getRequiredUserProfile(userId)` 是 F5 / F7 读取求职目标的唯一入口，档案为空时抛 1101，后续模块直接复用，不要重复建表或另写校验；助手侧的用户背景（昵称、求职目标）由系统提示词注入，不注册业务工具，档案只由用户在 `/profile` 页修改 |

字段只有两个，都是必填：

| 字段 | 必填 | 用在哪 |
|---|---|---|
| 目标岗位 | 是 | 模拟面试出题方向、训练计划 |
| 当前工作年限 | 是 | 决定问题深浅与难度起点 |

不设「目标公司」——求职者同时投多家公司，写死一家没有意义。不设「面试时间」——它是每次生成计划时的一次性输入（例如「3 天后」），不是长期档案字段。不设「目标难度」——难度由面试中的实际表现自适应。「当前阶段」也不设，工作年限已能表达。

阻塞规则：

- 未填写时，助手和简历中心照常可用；助手被问到岗位相关问题时提示先补。
- 进入模拟面试、生成训练计划时强制校验，未填写先跳 `/profile`，填完回到原入口。
- 未填写时每次登录进入应用壳后弹出一次提醒窗（可「稍后再说」跳过），填写保存后不再弹，直到档案被清空；
  提醒窗只是入口提示，不阻塞其它操作。

### F5 模拟面试

| 项 | 说明 |
|---|---|
| 用户操作 | 从「模拟面试」入口进来直接开始作答，**不需要选模式**（模式由系统决定，用户不选） |
| 题型 | 八股、项目、综合三类都会出，由面试 Agent 按目标岗位与工作年限混合搭配；参考配比 4:2:2，可按岗位微调 |
| 题量 | 默认 8 题，配置项 `app.interview.question-count` |
| 难度 | 起始难度由工作年限决定，之后**逐步上调**：答得好上调一级，答得一般持平；不因答错而下调到低于起始难度 |
| 系统产出 | 一轮一道主问题；按回答内容决定追问或换题；难度与进度实时可见 |
| 依赖 | F1（用默认简历）、F4（必填）；F2 的「可能被追问点」可作为出题素材，非硬依赖 |
| 规模 | L |
| 页面 | 会话（scene `INTERVIEW`） |
| Harness 能力 | 面试 Agent（本场景专属）、子 Agent「评分」、Session、SSE 流式、Tool、Compaction |

追问与换题规则（按用户这一题的表现三选一）：

| 表现 | 处理 | 难度 |
|---|---|---|
| 答到要点 | 就回答里的关键点追问一层，再进入下一题 | 上调一级 |
| 答得有遗漏 | 只追问遗漏的那一点 | 持平 |
| 完全不会或答错 | 这道题**记为错题**，不再追这道题涉及的知识点，直接换一道新题 | 持平，必要时下调一级 |

关键点：错题不纠缠。用户说不了解或答错时，继续围绕这道题的知识点追问只会让他更卡，正确做法是记下来、换题，留到 F6 的薄弱点清单和 F7 的训练计划里补。追问必须与用户回答相关，不按固定题库顺序出题，因此不预置题库。

### F6 面试点评与报告

| 项 | 说明 |
|---|---|
| 用户操作 | 答完一题立即看点评；面试结束看报告 |
| 系统产出 | 每题的正确点、遗漏点、错误点、表达问题、建议补充；错题清单；薄弱点清单；知识点掌握度；面试总结报告 |
| 依赖 | F5 |
| 规模 | M |
| 页面 | 面试会话内的点评面板 + 报告面板 |
| Harness 能力 | 子 Agent「评分」（与提问角色分离）、后台任务生成报告、Tool 落库、结构化输出、长期记忆写入 |
| 存储 | MySQL `interview_qa`、`interview_evaluation`、`knowledge_mastery`、`interview_report`（权威）+ Mem0（薄弱点跨会话召回） |

掌握度综合近期多次证据判定，不由单题决定。答错或被判定为「完全不会」的题在 `interview_qa.outcome` 记为 `WRONG`，既进报告里的错题清单，也作为薄弱点写入 `knowledge_mastery` 与 Mem0，供 F7 训练计划补强。

报告由后台任务生成，所以面试结束后面板先显示「报告生成中」，生成完成后（或用户刷新页面时）再展示报告内容，不阻塞用户继续操作。

### F7 训练计划

| 项 | 说明 |
|---|---|
| 用户操作 | 在计划页输入「还有几天、每天多长时间」，点生成；查看每日任务；收到每日提醒 |
| 系统产出 | 按天 / 主题 / 题型 / 难度划分的计划；表现变化时重规划并保留调整原因；每日提醒 |
| 依赖 | F6（薄弱点）、F4 |
| 规模 | L |
| 页面 | 资料库 → `/plans` |
| Harness 能力 | 计划 Agent、Plan Mode（只读规划阶段 + 人工确认）、Task List、HITL、长期记忆召回、定时任务（Quartz） |
| 存储 | MySQL `training_plan`、`training_task`、`training_reminder` |

**计划正文存 MySQL，不写工作区文件**：`plan_write` 落盘到服务器工作区，多用户会互相覆盖，因此只借用 Plan Mode 的「只读规划阶段 + 人工确认」语义，计划内容由业务表承载。

「还有几天」在生成计划时一次性输入，存进 `training_plan` 的截止日期字段，页面上的「剩余天数」由它实时算出；每日提醒写入 `training_reminder`，在计划页和侧栏「训练计划」入口上以未读角标展示。

## 4. Agent 架构

### 4.1 两条判断规则

**规则一：什么功能值得独立入口？** 只有「有状态的长流程」才配独立入口。一次性分析、问一句就出结论的事，不单独开会话。

| 类型 | 特征 | 形态 |
|---|---|---|
| 长流程 | 有明确阶段与结束条件、跨多轮存状态、产出可回访的资产、用户会反复进入 | 独立入口 + 专属 Agent |
| 一次性任务 | 贴一份材料、问一次、给一份结论 | 由助手 Agent 派子 Agent 完成 |
| 自由答疑 | 没有材料，就是聊 | 助手直接回答，必要时加载 Skill |

**规则二：什么时候派子 Agent？** 三条同时满足才派：材料长或上下文重；需要另一套提示词与工具；结果要回到当前对话继续用。

### 4.2 Agent 清单

| Agent | 触发方式 | 负责 |
|---|---|---|
| 助手 Agent | 会话（scene `ASSISTANT`），应用默认入口 | F8 自由问答；读简历/目标/薄弱点；派发下面两个分析子 Agent；F9 讲解与出题 |
| ├ 简历分析子 Agent | 由助手派发 | F2 简历诊断与优化建议 |
| └ 岗位匹配子 Agent | 由助手派发 | F3 对标目标 JD |
| 面试 Agent | 会话（scene `INTERVIEW`） | F5 出题与追问；派发评分子 Agent，产出 F6 点评与报告 |
| └ 评分子 Agent | 由面试 Agent 派发 | 对每题回答打分、识别薄弱点 |
| 计划 Agent | 计划页按钮触发，非会话 | F7 生成与重规划计划 |
| 提醒 Agent | 定时触发，非会话 | F7 每日提醒 |

### 4.3 为什么这么分

**简历优化、岗位匹配交给助手派子 Agent，不单独开入口**：

1. 它们是一次性任务——给一份简历或一段 JD，产出一份结论，不是需要跨多轮维持状态的流程。
2. 材料长，简历全文和 JD 都很占上下文，交给子 Agent 处理，主对话不被撑爆。
3. 可以并行——用户说「简历和这个 JD 一起看看」，助手同时派两个子 Agent，结果一起回来。
4. 结论要回到对话里继续用——用户看完会接着问「那我该补什么」，这是助手的对话。

**模拟面试单独开入口 + 专属 Agent**：它是有状态的长流程——一轮一题、按表现调难度、结束出报告，用户会反复进入，历史会话还要能回访。

**评分必须是子 Agent**：评分与提问必须分离（同一个 Agent 又当选手又当裁判）；评分需要另一套提示词与评分标准 Skill、只读题目与回答；结果要回到面试流程里接着问下一题。三条全中。

**辅导不拆子 Agent**：讲解就是助手的对话能力，加一个「讲解规范」Skill 和读薄弱点的 Tool 就够了。

**跨模块取数据不走子 Agent**：训练计划要用的简历、目标、历史薄弱点，都是别的模块已经存好的数据，用 Tool 读 MySQL / Mem0 即可。

### 4.4 入口与 Agent 的关系

| 东西 | 是什么 | 不是什么 |
|---|---|---|
| 前端入口 | 一个会话的起点，决定开场提示、右侧面板与用哪个 Agent | 不等于一个 Agent |
| 会话 scene | 前端展示 + 初始提示 + Agent 装配的选择键，本期只有 `ASSISTANT`、`INTERVIEW` | —— |
| 专属 Agent | 每个会话场景一套提示词与工具白名单 | —— |
| 子 Agent | 当前对话内部派出去的专业角色 | 不是独立入口 |

不启用「子 Agent 运行期暴露成入口」（`expose_to_user`）机制：入口统一由前端预设。

## 5. 前端界面结构

### 5.1 整体骨架

```
┌──────────────────┬──────────────────────────────────────────┐
│ 求职智能助手       │                                          │
│                  │                                          │
│ [+ 新建会话]      │                                          │
│ 模拟面试          │                                          │
│                  │                                          │
│ 最近会话          │              主内容区                     │
│  · 简历诊断…      │                                          │
│  · 面试练习…      │    助手会话 / 面试会话 / 资料库页面        │
│  · …             │                                          │
│                  │                                          │
│ 资料库            │                                          │
│  · 我的简历       │                                          │
│  · 训练计划       │                                          │
│                  │                                          │
│ 求职目标 ●        │                                          │
│                  │                                          │
│ 张三 / 退出登录    │                                          │
└──────────────────┴──────────────────────────────────────────┘
```

左侧栏四组：会话入口、最近会话、资料库、求职目标；底部是用户信息与退出。「求职目标」未填写时带红点，
且每次登录进入应用壳后弹出一次提醒窗（可跳过），引导去填写。

### 5.2 每个页面的构成

| 页面 | 路由 | 内容 |
|---|---|---|
| 助手会话 | `/chat`、`/chat/:sessionId` | 消息流 + 输入框；**空会话时显示引导卡片**；输入框上方四个快捷指令 |
| 模拟面试会话 | `/chat/:sessionId`（scene `INTERVIEW`） | 顶部进度（第 n 题 / 共 N 题、当前难度）；消息区；答完一题在气泡下方显示点评卡片；结束时显示报告卡片 |
| 我的简历 | `/resumes`、`/resumes/:id/edit` | 简历列表（标题、默认标记、解析状态）+ 上传 / 新建；每行有「设为默认」「编辑」「删除」「**诊断**」，点诊断跳到助手会话并发起诊断 |
| 训练计划 | `/plans` | 计划概览（目标、剩余天数）+ 按天分组的任务清单（可勾选）+「生成 / 重新规划」+ 今日提醒 |
| 求职目标 | `/profile` | 表单：目标岗位、当前工作年限；保存 |

简历是先在资料库上传、再在助手里使用：助手默认用「默认简历」，用户也可以说「用第二份简历诊断」。

### 5.3 空会话引导卡片

新用户第一次进助手，消息区显示一张卡片，按完成度引导，避免面对一个空白输入框：

1. 求职目标没填 → 「先填目标岗位和工作年限」→ 跳 `/profile`
2. 简历没上传 → 「上传一份简历」→ 跳 `/resumes`
3. 都完成 → 显示四个快捷指令：诊断我的简历 / 分析这个 JD 和我的简历 / 我上次面试哪里最差 / 讲讲我的薄弱点

快捷指令只是往当前会话发一句话，不是独立 Agent、不新建其它场景。

引导卡片与登录提醒窗分工：登录提醒窗在求职目标未填写时每次登录弹一次，只做入口提醒；引导卡片只在空会话时
展示，按完成度给出下一步。两者互不替代。

### 6.2 框架扩展的部署形态

| 扩展 | 作用 | 部署形态 |

### 6.3 明确不用的

| 能力 | 原因 |
|---|---|
| Workspace 文件式记忆（`MEMORY.md`、`memory/*.md`） | 网页版多用户系统共用一个工作区，用户之间会串数据 |
| Plan Mode 的工作区文件落盘 | 同上，计划正文改存 MySQL |
| 子 Agent 暴露给用户（`expose_to_user`） | 入口统一由前端预设 |
| 文件读写与 Shell 工具 | 向模型暴露服务器文件系统与命令执行是纯风险 |
| 大结果卸载（`ToolResultEvictionConfig`） | 卸载后要靠 `read_file` 取回全文，而本项目关闭了文件读写工具，模型拿不回来，等于丢数据；卸载还会往共享工作区落盘，多用户会串数据。业务 Tool 自己控制返回长度即可 |
| Sandbox 沙箱与编程题 | 本期不做在线编程题 |
| MCP | 本期不接外部工具 |
| Channels（飞书 / 钉钉等） | 提醒只做站内，不做 IM 推送 |
| 框架 RAG（`Knowledge` / `RAGMode`） | 没有检索场景；该模块在 2.0 已标记 forRemoval |
| 框架自带 `LongTermMemory` 文件实现 | 长期记忆统一走 Mem0 |
| `teamsMode` | 团队协作模式，本场景用不上 |

### 6.4 提示词与 Skill 的存放

多 Agent 之后提示词分三类，各归各的地方：

| 类型 | 内容 | 存哪 | 改完要不要发版 |
|---|---|---|---|
| Agent 系统提示词 | 角色、职责边界、语气、工具使用要求、安全边界 | 仓库 `backend/src/main/resources/prompts/{agent}.md` | 要 |
| 业务规则（Skill） | 分析规范、出题规则、评价标准、讲解规范 | MySQL `agentscope_skills`（`MysqlSkillRepository`） | 不用，热生效 |
| 可调参数 | 最大轮数、召回条数、题目数量 | `application*.yml` | 不用（重启生效） |

分界线一句话：**提示词写「角色」，Skill 写「做法」**——提示词回答「你是谁、边界在哪」，Skill 回答「这件事按什么标准做」。

提示词文件清单：

| 文件 | 对应 Agent |
|---|---|
| `prompts/assistant.md` | 助手 Agent |
| `prompts/interviewer.md` | 面试 Agent |
| `prompts/planner.md` | 计划 Agent |
| `prompts/reminder.md` | 提醒 Agent |
| `prompts/sub-resume-analyst.md` | 简历分析子 Agent |
| `prompts/sub-job-match.md` | 岗位匹配子 Agent |
| `prompts/sub-evaluator.md` | 评分子 Agent |

初版状态（2026-09-28）：**七个提示词文件已全部写入** `backend/src/main/resources/prompts/`。

落地进度（2026-09-29，F2）：`resume-analysis` 的默认内容已随 F2 落到 `agentscope_skills` 表，初始化脚本在 `sql/career_assistant.sql` 末尾（幂等，重复执行不产生重复数据）；其余 Skill 仍按上述清单随各自模块落地。

初始 Skill 清单：

| Skill | 内容 | 谁用 |
|---|---|---|
| `resume-analysis` | 简历分析规范：维度、评分口径、输出结构 | 简历分析子 Agent |
| `job-match` | 岗位匹配规则：命中与缺失关键词的判定、维度定义 | 岗位匹配子 Agent |
| `interview-questioning` | 出题规则：八股/项目/综合的配比、难度阶梯、追问与换题的判定条件（含「答错就记错题换题」） | 面试 Agent |
| `answer-evaluation` | 评价标准：五个维度的判定口径、掌握度计算方式 | 评分子 Agent |
| `tutoring` | 讲解规范：先定位、再类比、再举例、最后出一道练习 | 助手 Agent |

为什么系统提示词不放 `application.yml`：一个 Agent 一段多行文本，七八个 Agent 会把配置文件变成提示词仓库，改一个字要动整份配置，diff 与 review 都不方便。

为什么系统提示词不放数据库：它和代码强耦合，引用工具名、输出结构和 Agent 名，存库会出现「提示词里写的还是老工具名」的漂移；放文件跟着代码版本走，不一致在启动时就会暴露。

**不做管理后台**：真正需要运营的只有 Skill 规则，而 Skill 已有 MySQL 仓库、改完热生效。开发期用幂等初始化脚本写入默认 Skill，临时调整直接改表。管理后台要额外做权限、审计、发布流程，收益远小于成本。

落地进度：助手提示词已从 `application.yml` 迁到 `prompts/assistant.md`，配置项改为 `app.agent.prompt-location`，`SystemPromptProviderImpl` 按位置读文件、进程内缓存、读不到时退回兜底提示词。**已完成（2026-09-29，F2）**：`SystemPromptProvider` 已改为按 Agent 取（`prompt(agentId)`），`career-assistant` 与 `resume-analyst` 各取各的文件、各自独立缓存、各自兜底；六个子 Agent 提示词文件全部就位。

## 7. 数据存储分工

| 数据 | 存在哪 |
|---|---|
| Agent 会话状态与上下文 | Redis（Redisson） |
| 会话元数据、对话消息 | MySQL（`chat_session`、`assistant_message`） |
| 账号与令牌 | MySQL（`sys_user`、`sys_token`、`sys_refresh_token`） |
| 简历正文与元数据 | MySQL（`resume`）；原始文件在 MinIO |
| 求职目标 | MySQL（`user_profile`） |
| 训练计划与每日任务 | MySQL（`training_plan`、`training_task`） |
| 训练提醒 | MySQL（`training_reminder`） |
| 面试问答、点评、掌握度 | MySQL（`interview_qa`、`interview_evaluation`、`knowledge_mastery`，权威数据） |
| 面试报告 | MySQL（`interview_report`） |
| 薄弱点与偏好（跨会话召回） | Mem0 服务 |
| Skill 内容 | MySQL（`agentscope_skills`） |

原则：**结构化业务数据以 MySQL 为唯一权威**，Mem0 只存可跨会话召回的薄弱点与偏好；Redis 只放会话运行状态，不承担业务事实。

## 10. 协作约定

### 10.1 契约上收、实现下放

| 谁负责 | 内容 |
|---|---|
| 总排期（本文档 + `docs/技术约定.md`） | 模块顺序、表结构、接口清单、SSE 事件、错误码号段、共享文件清单、每个模块的完成定义 |
| 开发窗口 | 模块内部的拆分、类与包设计、提交节奏、单元测试、实现细节 |

也就是说：**模块之间怎么对接由上收的契约定死，模块内部怎么排怎么拆由开发窗口自己定。** 这样并行开发不会跑偏，也不需要把每个模块的内部计划都写进总排期。

三条硬约束：

1. 一个模块 = 一个窗口 = 一个分支，从 `dev` 新开：`dev-feature/<年月日>-<功能名>`。
2. 契约（表结构、接口、错误码）冻结后才能开工；中途要改契约，先改文档再改代码。
3. **能力接入按第 9 节的顺序串行做**，因为都会动 `AgentFactory`、`pom.xml`、`application*.yml` 这些公共文件，不能两个窗口同时开。
