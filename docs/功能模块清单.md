# 功能模块清单

> 这份文档只回答一个问题：**这个网页应用有哪些功能模块、每个模块做到什么程度。**
>
> 划分维度是「用户能用的功能」，不是技术分层，也不是框架能力。记忆、Skill、计划模式、子 Agent 这类属于 AgentScope 框架自带的能力，统一放在第 4 节，**它们不是模块，不单独排期**。
>
> 维护方式：完成一个模块就把状态改成「已完成」并补上分支；新增功能追加到表格末尾，不改动已有行。

## 1. 项目定位

网页版求职面试训练助手。用户注册后按下面这条链路使用：

1. 上传或在线填写简历（F1）
2. 填写求职目标：目标岗位、目标公司、面试时间、目标难度、当前阶段（F4）
3. 让系统诊断简历、针对目标 JD 做匹配（F2 / F3）
4. 按目标岗位做模拟面试，系统根据回答动态追问（F5）
5. 每一轮回答得到点评，沉淀薄弱点与掌握度（F6）
6. 系统按薄弱点生成训练计划，并随表现变化调整（F7）
7. 换一个会话继续练时，系统记得住薄弱点和偏好（框架能力：长期记忆）

系统部署在服务器上供多人在线使用，数据按账号隔离，不是安装在用户本地的工具。

## 4. Harness 能力使用清单

这是本项目的重点：**尽可能用上 AgentScope Java 2 的 Harness 能力，但每一项都要有真实场景支撑，不为用而用。**

### 4.1 已经用上的

| 能力 | 用在哪 |
|---|---|
| HarnessAgent 主入口 | 全部对话 |
| Session / AgentState | 会话状态存 Redis |
| Streaming / SSE | 全部对话的流式输出 |
| Middleware（自定义） | 系统提示词注入、埋点 |
| Tool 白名单（ToolsConfig） | 每个 Agent 只暴露自己的工具，框架默认工具必须显式 deny |
| Tool | 已有 1 个示例工具（`get_current_user`，将被 F4 的档案工具替换） |

### 4.2 计划用上的（每项都对应一个真实场景）

| 能力 | 用在哪 | 场景说明 |
|---|---|---|
| 业务 Tool | F2 / F3 / F4 / F5 / F6 / F7 | 读简历、读档案、存点评、存薄弱点 |
| 子 Agent | F5、F6 | 一场面试天然有两个角色："出题追问"和"评价打分"；评价必须独立于提问，否则就是又当选手又当裁判 |
| 子 Agent 暴露给用户 | F5 面试中 | 用户面试卡住，想单独问问某个知识点：主 Agent 把 Tutor 子 Agent 暴露成一个可点入口，用户直接和它聊，聊完回到面试继续 |
| 后台子 Agent 任务 | F6 | 一场面试结束生成完整报告比较慢，交给后台跑，用户先看到"报告生成中" |
| Plan Mode | F7 | "3 天后面 Java 实习，每天 2 小时"这类复杂目标，天然是"先规划后执行"，计划阶段只读 + 人工确认 |
| Task List | F7 | 计划里的每日任务要能跟踪完成情况 |
| HITL | F7、F4 | 覆盖已有计划、修改求职目标前要人工确认 |
| Skill | F2、F5、F6 | "简历分析规范""出题规则""评价标准"这类规则要可复用、可替换，改规则不用改主流程 |
| 长期记忆 | F6 → F7 | 第一天暴露的 Redis 薄弱点，第二天新建会话要能接着练 |
| Compaction | F5 | 一场 10 轮以上的面试，上下文必须压缩 |
| Tool Result Eviction | F2、F5 | 简历全文、长 JD 直接进上下文会爆，大结果卸载到磁盘只留引用 |
| Permission（按场景分工具集） | 全部 | 不同场景给不同工具集，简历类工具不该出现在面试场景里 |

### 4.3 要补功能才能用上的（需要你决定）

| 能力 | 需要新增什么功能 | 场景说明 | 代价 |
|---|---|---|---|
| Sandbox（沙箱执行代码） | 编程题训练 | 面试中出一道算法题，用户在网页里写代码，沙箱跑测试用例给结果。这是 Java 面试准备里最真实的场景 | 要加代码编辑区、判题与沙箱资源 |
| MCP | 外部岗位信息 | 通过 MCP 接外部岗位服务，让岗位匹配拿到更真实的 JD | 要有可用的 MCP 服务，多一层外部依赖 |
| 定时任务 | 训练提醒 | 按训练计划每天提醒用户今天的任务 | 要加通知入口 |
| Channels（飞书/钉钉） | 提醒推送渠道 | 把训练提醒推到用户常用的 IM | 需要企业账号与回调配置 |

### 4.4 明确不用的

| 能力 | 原因 |
|---|---|
| Workspace 文件式记忆（`MEMORY.md`、`memory/*.md`） | 这是网页版多用户系统，文件写在服务器工作区，用户之间会串数据 |
| 文件读写与 Shell 工具 | 向模型暴露服务器文件系统和命令执行是纯风险，本产品没有这个需求 |
| 框架 RAG（`Knowledge` / `RAGMode`） | 没有检索场景；且该模块在 2.0 已标记 forRemoval、正在重写 |
| 框架自带的 `LongTermMemory` 文件实现 | 同上，长期记忆走 Mem0 |
| `teamsMode` | 团队协作模式，本项目用不上 |

### 4.5 两个多租户注意事项

1. **长期记忆**：不用工作区文件，走 Mem0，`user_id` 是必填维度，天然按用户隔离。框架有 `agentscope-extensions-mem0` 扩展，2.0.3 版本可用。
2. **Plan Mode 的计划文件**：`plan_write` 是往工作区写 `plans/PLAN.md`，也是文件，多用户共用一台服务器同样会互相覆盖。两种解法：给每个用户单独的工作区目录，或者计划正文存我们自己的 MySQL 表、只借 Plan Mode 的"只读规划阶段 + 人工确认"语义。**待定。**

## 5. Agent 架构：一个主 Agent，多个子 Agent

### 框架是怎么工作的

AgentScope Java 2 的 HarnessAgent 里，子 Agent 是这么用的：

- 系统里只有**一个主 Agent**（CareerAgent），用户直接跟它对话。
- 主 Agent 需要专业能力时，自己调用 `agent_spawn(agent_id="interviewer", task="...")` 把子 Agent 派出去干活。子 Agent 是临时实例，有自己的会话，结果以工具结果的形式回到主 Agent。
- 子 Agent **默认对用户不可见**，只是主 Agent 的内部工具。
- 如果主 Agent 判断某个子 Agent 值得让用户直接聊，可以带 `expose_to_user=true` 派发；框架会把它注册成一个**用户可寻址的入口**，并通过 SSE 推出 `SubagentExposedEvent`（带 `subagentId`、`agentId`、`label`）。前端收到这个事件就能在界面上加一条新入口，之后用户的消息可以直接发给这个子 Agent、绕过主 Agent。
- 子 Agent 声明方式有三种：工作区里的 `subagents/*.md`、代码里的 `builder.subagent(...)`、远程 URL。本项目不用工作区，走代码声明。

结论：**入口不是设计期写死的，可以是运行期由主 Agent 委派时生成的。**

### 入口和 Agent 的关系

| 东西 | 是什么 | 不是什么 |
|---|---|---|
| 前端入口 | 一个会话的起点，决定开场提示和右侧面板 | 不是一个 Agent |
| 会话 scene | 前端展示与初始提示的标记 | 不是 Agent 身份 |
| 主 Agent | 唯一的大脑，始终是它在跟用户对话 | —— |
| 子 Agent | 主 Agent 运行中派出去的角色 | 不是一个个独立入口 |

从「模拟面试」入口进来，仍然是主 Agent 在对话，只是这次它会派 Interviewer、Evaluator 子 Agent 去干活。

### 三种做法

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A 单入口 | 只留「通用助手」一个入口，用户说什么，主 Agent 自己判断要不要派子 Agent | 最贴框架模型，也最贴最初的设想；入口不需要预先设计 | 用户每次要自己说清楚要干什么；报告类结构化产出没有面板可放；一场长面试全挤在一个会话里 |
| B 单入口 + 快捷入口 | 「通用助手」是默认入口，另外每个功能给一个快捷入口，本质是「带预置开场白的新会话」，Agent 始终是同一个主 Agent | 点一下就进对场景；报告有专属面板；仍然只有一个主 Agent 在委派 | 提示词里要写清每个 scene 的初始行为 |
| C 运行期生成入口 | 不预设入口，主 Agent 派子 Agent 时用 `expose_to_user=true` 把它变成入口 | 完全由 Agent 决定，最灵活 | 用户不知道该点什么；每次都要先聊几句；难调试 |

**建议 B，并把 C 的机制限定在一个真实场景里使用**（用户面试卡住时，主 Agent 把 Tutor 子 Agent 暴露成一个新入口，用户直接跟它聊）。这样三种机制都用上了，又不会让用户面对一个不知道该点什么的界面。选 B 时 `scene` 的语义就是「会话起点 + 面板类型」，不是「Agent 类型」。

## 6. 前端入口与页面结构

整体是「左侧栏 + 主内容区」。左侧栏分四组，每个功能模块都有明确入口：

```
功能入口（点一下 = 新建对应场景的会话）
  通用助手  →  ASSISTANT
  简历优化  →  DIAGNOSIS
  岗位匹配  →  MATCH
  模拟面试  →  INTERVIEW
  专项辅导  →  TUTOR（可选，未开放前不显示）

最近会话（历史列表，向下滚动加载更早的会话）

资料库（独立页面）
  我的简历  →  /resumes
  训练计划  →  /plans

求职目标  →  /profile
```

| 模块 | 入口位置 | 点击后 | 路由 |
|---|---|---|---|
| F8 通用助手 | 功能入口 | 新建 ASSISTANT 会话 | `/chat/:sessionId` |
| F2 简历优化 | 功能入口 | 新建 DIAGNOSIS 会话 | `/chat/:sessionId` |
| F3 岗位匹配 | 功能入口 | 新建 MATCH 会话 | `/chat/:sessionId` |
| F5 模拟面试 | 功能入口 | 新建 INTERVIEW 会话 | `/chat/:sessionId` |
| F9 专项辅导 | 功能入口 | 新建 TUTOR 会话 | `/chat/:sessionId` |
| F1 简历中心 | 资料库 | 简历列表 / 编辑页 | `/resumes`、`/resumes/:id/edit` |
| F7 训练计划 | 资料库 | 计划页 | `/plans` |
| F4 求职目标 | 左侧栏底部 | 设置页 | `/profile` |

规则：

1. 一个会话有且只有一个场景，场景决定右侧渲染哪个面板（`ChatView.vue` 的 `SCENE_PANELS`）。
2. 场景没做完的入口**不显示**，不做一个点了会报错的按钮。
3. 保留「新建会话」按钮，等价于新建一个通用助手会话。
4. 不新增顶层独立页面，所有页面都在应用壳内。

### 求职目标是必填

岗位匹配、模拟面试、训练计划都要用目标岗位，所以这几个字段按下面处理：

| 字段 | 是否必填 | 用在哪 |
|---|---|---|
| 目标岗位 | 必填 | 岗位匹配、模拟面试、训练计划 |
| 面试时间 | 必填 | 训练计划 |
| 目标公司 | 选填 | 出题偏向、面试报告 |
| 目标难度 | 选填（默认中级） | 模拟面试的出题起点 |
| 当前求职阶段 | 选填 | 训练计划 |

未填写时的行为：

- 通用助手、简历中心、简历优化照常可用，不拦。
- 点击岗位匹配 / 模拟面试 / 训练计划时，跳到求职目标页并提示「先填写目标岗位」，填完再回到原来的入口。
- 首次登录后如果没填过，进入应用时引导填写一次，允许跳过；跳过后按上一条每次拦截提示。

### 用户信息工具要改

现在的 `get_current_user` 只返回 `userId` 和 `nickname`，模型拿不到目标岗位，做不了出题和匹配。按原始文档 FR-01，工具应该是读写求职档案：

| 工具 | 类型 | 内容 |
|---|---|---|
| `get_user_profile` | 只读 | 目标岗位、目标公司、面试时间、目标难度、当前求职阶段、默认简历 |
| `update_user_profile` | 写 | 更新上述字段，危险操作走人工确认 |

`get_current_user` 可以删掉：昵称不是业务数据，注入系统提示词即可，不值得占一个工具位。

## 7. 开发顺序建议

| 批次 | 模块 | 理由 | 练到的 Harness 能力 |
|---|---|---|---|
| 第一批 | F4 求职目标 + F2 简历优化 | F1 已完成；F4 很小，F2 直接复用简历解析结果，能最快跑通「上传简历 → 得到诊断」的完整链路 | 业务 Tool、Skill、Tool Result Eviction、HITL |
| 第二批 | F3 岗位匹配 + F5 模拟面试 | 两块互不依赖，可并行；F5 需要 F4 的目标岗位来出题 | 子 Agent、Compaction、Permission 分工具集 |
| 第三批 | F6 面试点评与报告 → F7 训练计划 | F6 依赖 F5，F7 依赖 F6 产出的薄弱点，串行推进 | 后台子 Agent 任务、长期记忆、Plan Mode、Task List |
| 第四批 | F9 专项辅导 | 可选，视时间而定 | 子 Agent 暴露给用户（`expose_to_user`） |
| 随时 | 长期记忆接入 | F6 一开始产出薄弱点就能接 | 长期记忆（Mem0） |

## 8. 明确不做

| 不做的东西 | 原因 |
|---|---|
| 知识点树与题库 | 追问按用户回答动态生成，不预置固定题库、不做题库浏览页 |
| 岗位 JD 独立管理 | JD 在对话里粘贴即可，不单独建表、不做岗位列表 |
| RAG / 向量检索 | 原始需求没有；框架的 RAG 模块本身在 2.0 标注为待重写 |
| 评测与回归平台 | 原始需求没有，属于工程附加项 |
| Workspace 文件式长期记忆 | 网页版多用户共用服务器，按用户隔离成本高 |
| MCP 外部工具 | 本期不需要，先把本地业务 Tool 做好 |
